# Workflow loop — resolve / suppress / anti-gaming (design)

**Status:** spec, 2026-05-29
**Builds on:** `docs/superpowers/specs/2026-05-01-rust-port-design.md`
**Slice:** v0.9 (the three sub-features ship together — they share one state-model change)

## Goal

Turn `dslp` from a scanner into a usable agent harness. Today an agent can `scan`, see `findings`, and get `next` — but the only way to make an issue go away is to fix the code and rescan the whole project. That's slow and gives no way to say "I acknowledge this but won't fix it." This slice adds:

1. `dslp resolve <fingerprint>` — optimistically mark an issue fixed so `next` advances without a rescan
2. `dslp suppress <fingerprint> --reason "..."` — dismiss an issue as wontfix (reason required)
3. Lenient vs strict score split — so dismissing issues can't game the headline number

## Decision 1 — Issue status model

Replace `Issue.resolved: bool` with an explicit enum:

```rust
pub enum Status {
    Open,                                  // counts against the score, appears in `next`
    Resolved,                              // fixed (pending rescan confirmation)
    Wontfix { reason: String, at: DateTime<Utc> },  // dismissed, standing decision
}
```

An issue is "actionable" iff `Status::Open`. `next` and `findings` show only Open issues.

**State schema bumps to version 2.** Old v1 state files (which had `resolved: bool`) are discarded on load — `.dslp/state.json` is gitignored local cache, regenerated by any scan, so there's no migration cost worth paying. Load detects `version != 2` and starts fresh.

## Decision 2 — How resolve/suppress interact with rescan (the subtle part)

`resolve` and `suppress` mutate persisted state directly (load → find by fingerprint → set status → save). They do NOT rescan. The next `scan` is the source of truth, and merge reconciles:

| Prior status | Re-detected by scan? | New status | Rationale |
|---|---|---|---|
| Open | yes | Open | unchanged |
| Open | no | Resolved | you fixed it; absence confirms |
| Resolved | yes | **Open** | regression — it came back, surface it again |
| Resolved | no | Resolved | confirmed fixed |
| Wontfix | yes | **Wontfix** (preserved) | standing decision survives rescans |
| Wontfix | no | Resolved | the dismissed thing is gone anyway |

The one non-obvious rule: **Resolved + re-detected → reopened.** `resolve` is optimistic; if the issue is still really there next scan, it honestly comes back. Wontfix is the opposite — a durable decision that survives rescans.

## Decision 3 — Lenient vs strict scoring

Both use the existing formula `100 * exp(-penalty / (size_kloc * 25))`. They differ only in which issues contribute penalty:

- **Lenient** = penalty from Open issues only (Resolved and Wontfix excluded)
- **Strict** = penalty from Open **+ Wontfix** issues (only Resolved excluded)
- **gap** = lenient − strict (always ≥ 0)

Consequence: you can drive *lenient* to 100 by suppressing every issue, but *strict* stays low and the gap exposes exactly how much you swept under the rug. A genuinely clean codebase has lenient == strict == 100, gap == 0. This is the anti-gaming mechanic, matching desloppify's "wontfix widens the gap."

Scoring must therefore work from `[Issue]` (which carry status), not just `[Finding]`. Refactor `score()` to take an iterator of `(Severity, counts_lenient: bool, counts_strict: bool)` so both scan-time and post-mutation paths share it.

## Decision 4 — CLI surface

```
dslp resolve <fingerprint>          # prefix match allowed (8-char fp is unique enough)
dslp suppress <fingerprint> --reason "<text>"   # reason required; errors without it
dslp score                          # now prints: lenient / strict / gap
dslp score --json                   # { lenient, strict, gap, total_loc, ... }
```

Fingerprint args accept a unique prefix (the 8-char fp we already print). Ambiguous prefix → error listing matches. Unknown fp → exit 1 with message.

After `resolve`/`suppress`, recompute lenient/strict from the mutated issue list and print the new scores so the agent sees immediate feedback.

`next` / `findings` / `scan` output gain a wontfix-aware note where useful (e.g. `score` shows "N wontfix").

## Testing

- Status enum serde roundtrip; v1-state-discarded-on-load.
- Merge truth table: all six rows above as explicit unit tests.
- Scoring: lenient ≥ strict always; suppressing an Open issue raises lenient, leaves strict unchanged, widens gap; resolving raises both.
- CLI E2E: scan → suppress one fp → score shows gap → rescan → wontfix preserved.
- Prefix matching: unique prefix resolves, ambiguous prefix errors.
